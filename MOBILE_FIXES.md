# Mobile usability and connectivity · 0.3.0

The welcome screen renders a bundled Three.js meal scene in an isolated WebView on Android and a sandboxed iframe in the browser. Geometry, materials, renderer code, and fallback art are local; there is no CDN dependency. The scene grows into view, gently rotates, and shrinks during exit. Native text fades with it. Reduced motion is respected, and missing WebGL falls back to a leaf. Startup waits for local storage hydration, offers an immediate entry button when ready, and releases the renderer on unmount.

The tab bar now derives its total height and bottom padding from safe-area insets instead of placing labels in Android's navigation area. It hides while a keyboard is open. Shared sheets reserve the keyboard's overlapping area, use a stable available height, and keep their body scrollable. Ingredient search uses that single scroll surface, dismisses the keyboard when a food is chosen, and supports shorter visible viewports. Android uses resize keyboard mode. Safe areas remain reserved when the keyboard is closed.

Connection indicators use Expo Network and update when the device changes connectivity. Online status indicates a network connection, not a guarantee that a particular third-party service is reachable. Actual requests have timeouts, retry messages, and offline-safe fallbacks. Wi-Fi without internet can still produce a request error; it does not disable the bundled catalog.

Barcode lookup first checks local foods, optionally tries the configured USDA proxy, and then uses the public Open Food Facts API. Public packaged-food search is also available when the private proxy is unconfigured. Successful lookups are persisted as source-linked food snapshots. Scanning the same package offline uses that saved record. Unknown records offer manual label entry, including caching the scanned barcode for future use. In-flight scans are guarded against duplicate camera callbacks. Camera denial offers settings/manual entry.

Only explicit per-100-g records are accepted from the public database. Missing nutrients remain unknown, and liquid/volume records are rejected rather than assigned an invented density. Community data must be checked against the package. The barcode shown in the supplied screenshot, `8964000061121`, returned an existing product record with no name or nutrition; that is handled as missing usable data. A live lookup of `3017620422003` returned a named product successfully during implementation.

[Open Food Facts](https://world.openfoodfacts.org/) product data is supplied under the [Open Database License](https://world.openfoodfacts.org/terms-of-use). Source attribution is retained in saved foods, shown in the food source panel, and included in backups. USDA catalog provenance remains unchanged. Public API calls send the explicit barcode/search query; onboarding preferences are not uploaded. See the [API documentation](https://openfoodfacts.github.io/openfoodfacts-server/api/) for coverage and rate limits. Barcode camera recognition happens on the device.

To regenerate the bundled 3D scene after editing `tools/welcome-scene.js`, run `node tools/build-welcome.cjs` from the repository root. Commit the generated `apps/mobile/src/data/welcome-html.json` together with the scene source. It retains Three.js license comments.

Core local recipes, catalog search, calculations, and previously cached products work offline. New product searches need internet and database coverage. USDA proxy searches still need operator configuration; real paid subscriptions require the existing Play/backend configuration. Connectivity does not create a paid entitlement.

Browser tests cover a shorter visible search area, startup, online product lookup, caching, and offline reuse. They do not emulate Samsung's system keyboard or establish actual Android WebView/TalkBack/navigation behavior. No Android device was connected during this change; verify both gesture and three-button navigation, keyboard resizing, camera permissions, and WebGL fallback on real devices before production release.
